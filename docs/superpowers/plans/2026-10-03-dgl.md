# DevFest Got Latent (DGL) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Live audience voting for the DevFest Got Latent segment: phones vote 1 to 10 after each 90 s act, a stage screen runs the timer and the reveal, and an admin console drives the show from the server.

**Architecture:** Show state, votes and admins live in Neon Postgres (`dgl_*` tables, created on first use like `/api/excited`). Every write is one SQL statement (data-modifying CTEs), so it is atomic over Neon's HTTP driver without transactions. Clients poll: the public state endpoint is CDN-cached for 1 s, so the DB sees about one read per second regardless of crowd size. The rules (state machine, permissions, scoring, the offline queue) are pure modules under `src/lib/dgl/`, tested with Vitest; DB code is tested against PGlite (real Postgres compiled to WASM).

**Tech Stack:** Next.js 16 App Router route handlers, `@neondatabase/serverless` (already installed), Tailwind v4 tokens, Motion (`LazyMotion` + `m` on DGL pages), Phosphor icons. New: `vitest`, `@electric-sql/pglite`, `tsx` (dev), `qrcode` + `@types/qrcode`.

**Spec:** `docs/superpowers/specs/2026-10-03-dgl.md` (transcription of the organisers' DGL SPEC.pdf). Project rules: `CLAUDE.md`, `docs/SPEC.md`.

**Timeline:** event is 10 Oct 2026. Tasks 1-10 and 14 are P0 (needed for the show). 11 (setup panel), 12 (kiosk) and 13 (service worker) are P1, in that order. Full rehearsal on 8 Oct.

## Global Constraints

- Before writing a route handler, read `node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/route.md` and `.../04-functions/cookies.md` (this Next has breaking changes; see AGENTS.md).
- All DGL facts and copy live in `src/data/dgl.ts`. Components never hardcode a string a person reads, a threshold or a duration.
- `PERFORMANCE_MS = 90_000`, `FINAL_COUNTDOWN_S = 10`, `MIN_VOTES = 5`. Scores are integers 1 to 10, validated on the server.
- Audience average: one decimal everywhere it is shown (`8.2 / 10`, `8.0 / 10`). Self score is an integer. "Perfect match" when `|self - audience|` rounds to `0.0`; otherwise "Difference 2.3" (absolute, one decimal).
- Exact spec copy: `Vote queued, waiting for connection`, `Vote recorded`, `Waiting for audience...`, `Perfect match`.
- Copy: sentence case, no em or en dashes (`grep -rnE "—|–" src/` stays empty), one label per CTA intent. "DevFest Got Latent" is a proper name and keeps its capitals.
- Server time is truth: every timestamp is written from the route's `Date.now()` passed in as `now: number`. Clients derive time from `endsAtMs` plus a clock offset measured against an uncached endpoint. Never from the client clock alone.
- Timestamps, averages and counts cross the DB boundary as numbers: select `extract(epoch from x) * 1000` as `float8`, `avg(...)::float8`, `count(*)::int`.
- No audience accounts. Voter id is an httpOnly cookie `dgl_voter` (UUID v4, `SameSite=Lax`, `Secure` in production, 1 year). Votes store no contestant name, only `performance_id`.
- Admin session cookie `dgl_admin`: `SameSite=Strict`, httpOnly, 12 h. Every admin POST also checks that `Origin` equals the request host.
- New env var `DGL_SECRET` (`openssl rand -hex 32`) in `.env` and in Vercel. It signs admin sessions and keys the IP hash. Raw IPs are never stored.
- The `/api/dgl/state` response must never `Set-Cookie` (Vercel will not cache a response that sets cookies).
- CLAUDE.md rules hold on DGL pages: Server Components by default, `'use client'` leaves only, animate values never branch on `useReducedMotion()` (only `transition` may), tokens from `@theme`, radius panels 24 / cards 20 / buttons pill / inputs 12, Phosphor regular, no `backdrop-filter` outside `.glass-live` (DGL pages use `.glass` only: nothing moves behind them), no WebGL, no loader.
- Work on a branch `feat/dgl` from `main`. Do not change the default or production branch.

## Review Focus

1. **A queued vote that reaches the server after voting stopped or moved on** (phone was offline, flushes later). Expected: server answers `closed`, the phone says it was not counted, and never shows "Vote recorded". Pinned by `castVote > rejects a vote for a closed or non-current performance` (Task 2) and `applyVoteResult > closed becomes rejected` (Task 7).
2. **A retry or a second tab after the first request actually succeeded** (timeout on a slow network, double tap). Expected: one row, and the second answer carries the first score so the UI shows "Vote recorded: 7", not an error. Pinned by `castVote > second vote from same voter returns duplicate with the first score` and `> concurrent duplicates insert one row` (Task 2), and `applyVoteResult > duplicate becomes recorded with the server score` (Task 7).
3. **Two admins pressing at once, or one double-clicking** (laptop dies, a second admin takes over). Expected: one transition happens. The other gets `409 stale` and the fresh state, never a double step such as stop then reveal. Pinned by `applyAction > stale version is rejected and changes nothing` (Task 3).
4. **Leaks through the public endpoint.** Expected: self score is absent before REVEAL; average is `null` under 5 votes (the admin still sees it); no voter or IP data. Pinned by `readPublicState > hides self score until reveal` and `> average null below MIN_VOTES` (Task 3).
5. **Cached state and clocks.** Expected: `/api/dgl/state` may be up to 2 s old, so the timer counts from `endsAtMs` with an offset from `/api/dgl/me`, and still reads 0:00 at the same moment on every phone even if a phone's clock is minutes wrong. Pinned by `clock > remainingMs uses the server offset` (Task 7) and `state route > sends CDN cache headers and no cookie` (Task 5).

## Design direction

Design read (taste skill): a single-purpose live voting companion for attendees in a packed hall, opened from a QR code on weak Wi-Fi, inheriting the site's dark spectrum-light language, leaning toward Tailwind tokens, `LazyMotion` and almost no decoration. The admin console is product UI: the taste skill's landing-page rules do not apply there; it follows the shape lock and tokens only.

| Surface | VARIANCE | MOTION | DENSITY | Why |
|---|---|---|---|---|
| `/dgl` audience | 3 | 3 | 3 | Vote in seconds, one hand, eyes back on stage |
| `/dgl/stage` projector | 6 | 6 | 2 | Read from the back of a hall; the reveal is the moment |
| `/dgl/admin`, `/dgl/kiosk` | 2 | 2 | 6 | Operator speed under pressure, works on a phone too |

Decisions:
- **Tap grid, no slider.** The spec allows either. Ten pill cells in a 5 × 2 grid, each at least 56 px tall. Pick, then one primary pill "Lock in 7". Two taps stop a fat-finger vote that can never be changed.
- **Neutral cells.** No red-to-green scale on the grid: colour would push votes. The selected cell is the primary-button white; the rest are `.glass-pill`.
- **State colour, from `PAL`:** blue = voting open, yellow = last 10 s, green = recorded, red = offline or rejected. One status dot only, on the connection pill, because it reports real state.
- **Live average after you vote.** The phone shows the count before you vote and the average after (or once voting closes), so early votes don't anchor later ones. The stage shows the count while voting and the average only at reveal. This is one flag, `DGL.showLiveAverage: "after-vote" | "always"`, in case the organisers want the spec's literal reading.
- **Reveal labels:** the stage uses the spec's "You / Audience" (the contestant reads it). Phones say "Own score / Audience", because the viewer is not the contestant.
- **Motion that carries meaning, and nothing else.** Phone: the selected cell scales to 1.04, and the recorded state cross-fades. Stage: the timer digits go yellow at 10 s and red at 3 s; at reveal the self score lands, then the audience number counts up over 1.2 s (a MotionValue), then the verdict fades in. Under reduced motion every `transition` is `{ duration: 0 }`, with the same end states.
- **One LightPipe per view, on the stage only:** a `ring` behind the timer in the phase colour, `run` off. Phones carry no light marks (weight and battery).

`castVote` is one statement. Its shape is the decision here:

```sql
WITH cur AS (SELECT p.id FROM dgl_show s JOIN dgl_performances p ON p.id = s.current_performance_id
             WHERE p.id = $1 AND p.status = 'VOTING'),
burst AS (SELECT count(*) AS n FROM dgl_votes WHERE performance_id = $1 AND ip_hash = $4
          AND created_at > to_timestamp($6 / 1000.0) - make_interval(secs => $7)),
ins AS (INSERT INTO dgl_votes (performance_id, voter_id, score, ip_hash, source, flagged, created_at)
        SELECT cur.id, $2, $3, $4, $5, (SELECT n FROM burst) >= $8, to_timestamp($6 / 1000.0) FROM cur
        ON CONFLICT (performance_id, voter_id) DO NOTHING RETURNING score)
SELECT (SELECT score FROM ins) AS inserted,
       (SELECT score FROM dgl_votes WHERE performance_id = $1 AND voter_id = $2) AS existing,
       (SELECT status FROM dgl_performances WHERE id = $1) AS status,
       EXISTS (SELECT 1 FROM cur) AS open
```

Map the result like this: `inserted` gives recorded; else `existing` gives duplicate; else `status = 'VOTING_PAUSED'` gives paused; else, if `open` (a concurrent insert won the conflict but our snapshot can't see it), re-select the existing score once and return duplicate; else closed. Throw on a non-integer score or one outside 1 to 10 before querying. A flagged vote still counts; flags only inform moderation.

### Task 3: Show state reads and admin actions

**Files:**
- Create: `src/lib/dgl/show.ts`
- Test: `tests/dgl/show.test.ts`

**Interfaces:**
- Consumes: `Db`, `ensureSchema` (Task 2); `effectivePhase`, `allowed`, `can`, `nextStatus`, `publicAverage`, `compareScores` (Task 1)
- Produces:
  - `type PublicState = { phase: Phase; performanceId: string | null; contestant: string | null; prompt: string | null; endsAtMs: number | null; votes: number; average: number | null; reveal: { self: number; audience: number | null; result: ReturnType<typeof compareScores> } | null }`
  - `type AdminState = PublicState & { version: number; serverNow: number; selfScore: number | null; rawAverage: number | null; flagged: number; excluded: number; kiosk: number; contestants: { id: string; name: string; sort: number; active: boolean; status: "upcoming" | "current" | "done" }[]; prompts: { id: string; text: string; active: boolean }[]; admins?: { id: string; name: string; role: Role; active: boolean }[]; audit?: { at: number; adminName: string; action: string; detail: unknown }[] }` (`admins` and `audit`, the last 50 entries, for SUPER_ADMIN only)
  - `readPublicState(db: Db, now: number): Promise<PublicState>`
  - `readAdminState(db: Db, admin: { id: string; role: Role }, now: number): Promise<AdminState>`
  - `type ActionResult = { ok: true; state: AdminState } | { ok: false; code: "forbidden" | "not_allowed" | "stale" | "invalid" | "needs_prompt" | "needs_self_score"; state: AdminState }`
  - `applyAction(db: Db, admin: { id: string; name: string; role: Role }, action: Action, version: number, now: number): Promise<ActionResult>`

Rules `applyAction` enforces, in order: `can(role)` else `forbidden`; input validation (score an integer 1 to 10, names and prompt 1 to 200 chars after trim, `confirm === "RESET"`) else `invalid`; for live actions, `allowed(effectivePhase(...))` else `not_allowed`; `startPerformance` needs a prompt (`needs_prompt`); `reveal` needs a self score (`needs_self_score`). Then one CTE statement that bumps `dgl_show.version`, but only `WHERE version = $version`, applies the change, and inserts the `dgl_audit` row. Zero rows updated means `stale`. Setup actions other than `resetShow` skip the version check, but every action writes an audit row.

What each live action writes:
- `selectContestant`: insert a performance (`READY`) and point the show at it.

  - `applyVoteResult(v: LocalVote, r: VoteResult | { status: "network" } | { status: "rate_limited" }): LocalVote`

It stops while `document.hidden`, polls immediately on `visibilitychange` and `online`, and calls `/api/dgl/me` on mount and every 60 s for `offset`. Fetches time out with `AbortSignal.timeout(6000)`. `connection` is `offline` when `navigator.onLine === false`, `reconnecting` after 2 consecutive failures, else `live`. It keeps the last good `state` through failures.
  - `useVote(state: PublicState | null): { local: LocalVote | null; submit(score: number): void }`. On mount it seeds `local` from `/api/dgl/me` (a server-known vote wins and is saved as recorded). It flushes a queued vote on `online`, on `visibilitychange`, every 4 s while queued, and when the phase becomes `VOTING`. It listens to the `storage` event so other tabs mirror the same vote. `submit` saves `queued` before the fetch, so a refresh mid-request keeps the queued vote.

`applyVoteResult` mapping (the honesty rule from the spec):

| Response | New local state | Copy key |
|---|---|---|
| recorded | recorded, score from server | `voteRecorded` |
| duplicate | recorded, score from server (not the local one) | `voteRecorded` |
| network / 5xx / rate_limited | queued (unchanged) | `voteQueued` |
| paused | queued, reason `paused` | `votePaused` |
| closed | rejected, reason `closed` | `voteNotCounted` |
