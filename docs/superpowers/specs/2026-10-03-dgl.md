# DevFest Got Latent (DGL): web experience spec

Transcribed from the organisers' "DGL SPEC.pdf" (condensed developer spec), 3 Oct 2026. Wording kept; numbering kept.

The goal: make the audience part of the performance. A contestant performs for 90 seconds, the room scores them from 1 to 10, and the DevFest website calculates the audience score live.

## 1. The 30 minute flow
Host introduces DGL. Contestant comes on stage. Contestant gets a challenge prompt. Contestant performs for 90 seconds. Host opens audience voting. Audience votes from 1 to 10 on the DevFest website. Host closes voting. Final audience average is shown. Contestant's own predicted score is revealed alongside it. Short reaction, then next contestant. No leaderboard.

## 2. Performance prompt
The DGL system does not need to build or manage the digital spinwheel. The contestant needs to receive a challenge prompt before the 90 second performance. If the developer cannot think of a suitable way to generate or select the prompt, the organisers provide it from the separate digital spinwheel.

## 3. Audience voting
Score is 1 to 10. Whole numbers only. Keep the voting UI extremely simple. User can use a slider or directly tap a number. Submit once; the vote cannot be changed. Audience sees the live average and number of votes. Audience does not see individual votes. Internal average can have decimals; display one decimal, for example 8.2 / 10. Do not use participant score in the audience average.

## 4. One vote per person
Do not implement one-public-IP-one-vote (venue Wi-Fi puts hundreds behind one IP). Use an anonymous browser/session voter ID. Server enforces one vote per voter per performance. Use IP as an additional anti-abuse signal. Add rate limiting. Multiple tabs must not create multiple votes. Refreshing must not create another vote. The server is the source of truth.

## 5. Admin panel
Controls the live activity: select current contestant, start performance, start voting, pause voting, stop voting, see live average and vote count, reveal final score, move to next contestant. Current state lives on the server, not only in the admin browser.

## 6. Admin rights
SUPER ADMIN: full setup, contestants, prompts, sessions, moderation and admin permissions. DGL OPERATOR: runs the activity and voting; cannot rewrite historical votes. HOST / STAGE CONTROLLER: controls the live show, timer, voting and reveal. Important admin actions are logged.

## 7. Participant score
Before the audience score is revealed, the contestant chooses their own score from 1 to 10. Stored separately; does not affect the audience average. Both revealed together. Examples: "You 8 | Audience 8 | Perfect match", "You 9 | Audience 6.7 | Difference 2.3".

## 8. Network / offline fallback
Online-first, but handle weak or lost connectivity. Basic DGL page loads on weak connectivity. Detect offline state. If a vote cannot reach the server, show "Vote queued, waiting for connection". Only show "Vote recorded" after server confirmation. Retry queued votes when connection returns. Never claim an offline vote was counted when it was not. Keep 1 or 2 volunteer devices for manual backup voting. If possible, use a dedicated venue network for DGL.

## 9. Edge cases
User joins after voting starts: show the current voting screen. User refreshes: previous vote stays locked. Multiple tabs: one vote accepted. Admin refreshes: state comes back from the server. Admin laptop dies: another authorised admin continues. Wrong contestant selected: pause voting before fixing it. Duplicate vote request: server rejects it. First few votes cause a big jump: show the real average. Suspicious spike: rate limiting helps flag abuse. Timer uses server time as the source of truth.

## 10. Timer and session states
Performance timer exactly 90 seconds, server time. Last 10 seconds visually obvious. At 0:00 the performance ends automatically. Suggested states: UPCOMING, READY, PERFORMING, VOTING, VOTING CLOSED, REVEAL, COMPLETED.

## 11. If nobody votes
Do not call one person's vote the audience score. Minimum vote threshold, for example 5. Before the threshold: "Waiting for audience...". Once reached: the actual average.

## 12. Not building
No leaderboard. No audience accounts or login. No public individual vote history. No decimal voting. No participant names attached to audience votes. No complicated voting flow.

Core principle: the website makes the performance more fun; it does not become the performance. Scan the QR, vote in a few seconds, get back to watching the stage.
